## Testing Methodologies
### Testing Functionality
#### *Techniques*
| Testing Techniques |                                                                Description                                                                |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Unit Testing       | Unit testing is the testing of each individual component or module of an operation, allowing faster identification of bugs and errors.    |
| Subsystem Testing  | Subsystem testing is the testing of multiple components or modules of a subsystem, to verify the components work as intended together.    |
| System Testing     | System testing is the testing of the entire software application, to ensure the application is ready for starting other forms of testing. |

#### *Applications*
***Unit Testing*** \
Unit testing was used in multiple areas of software development to debug errors in code, most notably in the **Map Generation** algorithm[^1]. It was used to ensure that the corridors and rooms generated correctly.

In the JoinRooms() method, I used extensive Unit testing to ensure it consistently autogenerated corridors between rooms correctly. This method consisted of two layers to the code marked by two while loops. I used Unit testing to ensure it correctly determined whether a corridor could spawn between two room coordinates.
```
JoinRooms()
{
    ...
    while ((newNode.x < dungeonWidth && newNode.x >= 0) && (newNode.y < dungeonHeight && newNode.y >= 0))
    {
        newNode += direction;
        if (intersectionCoords.Contains(newNode)) break;

        if (newNode.x == roomCoordToMapCoord(bossPosition).x && newNode.y >= roomCoordToMapCoord(bossPosition).y && newNode.y < roomCoordToMapCoord(bossPosition + Vector2Int.up * (bossCorridorLength + 1)).y && presetFinished) break;
        if (newNode == roomCoordToMapCoord(spawnPosition)) break;
        if (tree.Contains(newNode)) break;

        room = trees.FirstOrDefault(y => y.Contains(newNode));

        if (potentialIntersectionCoords.Contains(newNode)) nodeDistance++;
        if (room == null) continue;
        if (room.Count != smallestTree && tree.Count > smallTree) break;

        HashSet<Vector2Int> corridor = new HashSet<Vector2Int>();
        nodeDistance++;
        int distanceBetweenNodes = (int)roomCoordToMapCoord(Vector2Int.up).magnitude;

        for (int i = 1; i <= nodeDistance; i++)
        {
            corridor = CreateCorridor(node + (i - 1) * direction * distanceBetweenNodes, node + i * direction * distanceBetweenNodes);
            corridors.UnionWith(corridor);
        }

        if (!trees.Remove(tree))
        {
            int item = trees.FindIndex(y => y.SequenceEqual(tree));
            if (item != -1) trees.RemoveAt(item);
        }
        tree.AddRange(room);
        trees.Remove(room);
        trees.Add(tree);
        break;
    }
    ...
}
```
An early issue in the outside code block was that the loop would ran indefinitely, because it hadn't detected an exit condition. To solve this, I added an `iteration` variable to stop the code when it was determined that the loop would run infinitely.

Similarly to the JoinRooms() method, I also used Unit testing in the CreateExtraCorridors() method to ensure it also consistently autogenerated additional corridors between rooms correctly.

### Testing Features
#### *Techniques*
| Testing Techniques |                                                                                                                                           Description                                                                                                                                          |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Black-box Testing  | Black-box testing is the testing of game functionality without a technical understanding of the internal working of the code. In Black-box testing, the tester tests for correct input and output by the system.                                                                               |
| White-box Testing  | White-box testing is the testing of game functionality with a technical understanding of the internal working of the code. Testers test for errors, incorrect passing of data, or incorrect functionality.                                                                                     |
| Grey-box Testing   | Grey-box testing is a mix between Black-box testing and White-box testing, where the tester understands the basic structure of the code, such as algorithms, data structures, or architecture of the software. Grey-box testing is used to test more effectively and identify potential risks. |

### Testing Software
#### *Techniques*
| Testing Techniques |                                                                                                                                                          Description                                                                                                                                                          |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Quality Assurance  | Quality Assurance (QA) is the testing of the entire software, ensuring that it meets standards of design, implementation, and conformance. ***Alpha Testing*** \
Alpha testing occured during 14/06/25 - 20/06/25 by me.

Alpha testing was prominently used after I had completed the theoretical code for the Minotaur actions. After testing, I realised that the Minotaur's collider would frequently stop the player's collider from moving, thereby 'stun-locking' the player. It would also frequently run into walls and keep getting dazed, essentially 'stun-locking' itself. \
I solved these two problems by adding code where the Minotaur would move backwards after it detected a hitbox.
```
private void OnCollisionStay2D(Collision2D other)
{
    if (charging && other.gameObject.layer == 3)
    {
        StopCharging();
        stunned = true;
        stunCooldown = timeStunned;
        animator.SetBool("Stunned", true);
    }
    if (rigidbody2d.linearVelocity.sqrMagnitude == 0)
    {
        move = ((stunned) ? chargeDirection : Vector2.one) * -1 * speed;
    }
}
```

Another example of successful Alpha testing was when I was testing the final end screen of the game, where it showed whether the player won or lost the game. Code was supposed to change placeholder text in the UI to determined code, but two issues were identified when I first tested it. \
Firstly, there was an error in the code when referencing the Text component of each Text Gameobject.
```
[SerializeField]
private GameObject m_Endscreen;
[SerializeField]
private GameObject m_Result;
private TextMeshPro result;
[SerializeField]
private GameObject m_FlavourText;
private TextMeshPro flavourText;
[SerializeField]
private GameObject m_Return;
private TextMeshPro returnText;
```
The variables `result`, `flavourText`, and `returnText` were to be referenced by calling GetComponent<>() on the GameObjects above each Text component. However, each Text component was stored incorrectly, as the Text components in the GameObjects were `TextMeshProUGUI` instaed of `TextMeshPro`.

## Refining Code
Efficiency Measures Implemented
- Deleting limited-use variables
- Implementing OOP to reduce amount of code
- Using coroutines to run code alongside other code
	- PlayerController calls Pedestal.CreateCoin() to run alongside Update()
    - Minotaur calls Charge() to run alongside Update()
    - UIHandler calls FadeOpacity() to run outside of ElementSetVisible()

Optimisation Measures Implemented (doing things better)
- Utilising loops and deleting deprecated variables
- Allocating predetermined memory to known variables
- Overloading Methods to help readability
	- roomCoordToMapCoord() is overloaded to perform a single task for multiple different parameters
	- PaintTiles() is overloaded to perform a single task for multiple different parameters
